01Level 0 · Zero

Why Docker exists

Docker is a tool that packages an application together with everything it needs to run (code, runtime, libraries, system tools, settings) into one standard unit called a container. That container runs the same way on your laptop, a colleague's laptop, a test server and the cloud.

The problem: "It works on my machine"

Before containers, shipping software meant shipping instructions: "install Python 3.8, then these 40 libraries, set these variables, make sure OpenSSL is version X". Every machine was slightly different, so the same code behaved differently in different places.

  • Dependency conflicts. App A needs Node 16, App B needs Node 20, both on one server.
  • Environment drift. Dev laptops run macOS, the server runs Ubuntu, and the test box hasn't been patched in a year.
  • Slow onboarding. A new developer spends two days installing databases and tools before writing a line of code.
  • Heavy isolation. The only safe way to isolate apps was a full virtual machine per app, which costs gigabytes and minutes to boot.

The idea it borrowed: the shipping container

In 1956 Malcom McLean shipped goods in standard steel boxes on the Ideal X. Before that, dock workers loaded every sack, barrel and crate by hand. Afterwards, cranes, ships, trains and trucks only had to handle one shape of box, no matter what was inside. Docker applies the same rule to software: tools only need to know how to handle a container, not what language or framework is inside it. The whale-carrying-boxes logo comes from this idea.

Where it came from

Docker did not invent isolation. It packaged features that had been growing inside Unix and Linux for decades into a tool that was easy to use.

  1. 1979chroot in Unix V7 lets a process see a different root folder: the first file-system isolation.
  2. 2000FreeBSD Jails isolate processes, users and networking.
  3. 2004Solaris Zones bring OS-level virtualization to commercial Unix.
  4. 2006–08Google engineers build cgroups (limit CPU and memory per group of processes), merged into Linux 2.6.24. Linux namespaces mature in the same period.
  5. 2008LXC (Linux Containers) combines cgroups and namespaces, but is hard to use day to day.
  6. 2013Solomon Hykes at the PaaS company dotCloud demos Docker in a five-minute PyCon talk and open-sources it. dotCloud renames itself Docker, Inc. later that year.
  7. 2014Docker 1.0 ships. Docker replaces LXC with its own libcontainer. Docker acquires Fig, which becomes Docker Compose. Google announces Kubernetes.
  8. 2015The Open Container Initiative (OCI) forms to standardize image and runtime formats. Docker donates runc.
  9. 2017containerd is donated to the CNCF. Docker's open-source code becomes the Moby project.
  10. 2019Docker sells its enterprise business to Mirantis and refocuses on developer tools.
  11. 2020–22Kubernetes removes "dockershim" and talks to containerd directly. Docker-built images keep working because they follow the OCI standard.
  12. 2021Docker Desktop becomes paid for larger companies. It stays free for personal use, education, open source and small businesses.
  13. 2023+BuildKit becomes the default builder. docker init, Docker Scout (security scanning) and Testcontainers join the toolset.
In one sentence

Docker took existing Linux isolation features, added a simple file format (the Dockerfile), a layered image format and a public sharing hub, and made containers usable by every developer.

02Level 0 · Zero

Containers vs virtual machines

A virtual machine pretends to be a whole computer. Each VM boots its own full operating system on top of a hypervisor. A container is an ordinary process on the host that the Linux kernel fences off so it sees only its own files, network and process list. All containers share the host's kernel.

PropertyVirtual machineContainer
What is isolatedA whole emulated computerA process (files, network, PIDs, users)
KernelOwn guest kernel per VMShares the host's Linux kernel
Typical size1–20 GB5 MB – 1 GB
Start timeTens of seconds to minutesMilliseconds to seconds
Density per serverTensHundreds to thousands
Isolation strengthVery strong (hardware level)Strong, but a kernel bug affects all containers
Can run a different OSYes (Windows on Linux, etc.)Linux containers need a Linux kernel
Mac & Windows note

Containers need a Linux kernel. On macOS and Windows, Docker Desktop quietly runs one small Linux VM (on Windows, through WSL 2) and all your containers live inside it. You never manage that VM yourself.

03Level 1 · Concepts

The six core ideas

Everything in Docker is built from six nouns. Learn these and the rest is detail.

TermWhat it isEveryday analogy
DockerfileA text file of step-by-step instructions to build an imageA recipe
ImageA read-only, layered snapshot of a file system plus start-up settingsA frozen meal, or a class in programming
ContainerA running (or stopped) instance of an image, with its own writable layerThe meal heated and served, or an object made from the class
RegistryA server that stores and shares images (Docker Hub, GHCR, AWS ECR)An app store, or GitHub for images
VolumeStorage that lives outside the container so data survives deletionAn external hard drive

Dockerfile → Image
docker build follows the recipe and produces an image.
Image → Container
docker run starts a container from an image. One image can start many containers.
Image ⇄ Registry

Key mental model

Images are immutable. You never "edit" a running server; you change the Dockerfile, build a new image, and replace the old container with a new one. This is why deployments become repeatable.

04Level 1 · Concepts

Architecture: who does what

Docker uses a client–server design. The docker command you type is only a client. It sends requests to a background service, the Docker daemon (dockerd), which does the real work.

ComponentRole
docker CLITurns your commands into API calls. Can point at a remote host with docker context.
dockerdThe long-running daemon. Handles builds (through BuildKit), images, networks, volumes and the API.
containerdIndustry-standard container manager (also used by Kubernetes). Pulls and stores images, manages container lifecycles.
containerd-shimSits between containerd and each container so containers keep running if the daemon restarts.
runcThe low-level OCI runtime. Asks the kernel to create namespaces and cgroups, starts the process, then exits.
RegistryRemote image storage. Docker Hub is the default when you type a short name like nginx.
05Level 1 · Concepts

Images are stacks of layers

An image is not one big file. Each instruction in a Dockerfile that changes files (RUN, COPY, ADD) creates a new layer: a compressed record of the files that were added, changed or deleted. Docker stacks the layers with a union file system (usually overlay2) so they look like one normal folder tree.

Why layers matter

  • Disk savings. Ten containers from one 200 MB image use about 200 MB plus ten small writable layers, not 2 GB.
  • Faster downloads. If your server already has the python:3.12-slim layers, pulling a new version of your app downloads only the layers that changed.
  • Build caching. Docker skips any build step whose inputs haven't changed (see section 13).
  • Copy-on-write. When a container modifies a file from an image layer, Docker copies it up into the writable layer first. The image itself never changes.
Common trap

Deleting a file in a later layer does not shrink the image. The file still exists in the earlier layer and is only hidden. Clean up in the same RUN step that created the mess, or use a multi-stage build.

bash
docker image history python:3.12-slim   # list the layers and their sizes
docker image inspect python:3.12-slim   # full JSON metadata (env, cmd, layer digests)
06Level 1 · Concepts

The container lifecycle

A container moves through a small set of states. docker run is a shortcut for docker create plus docker start, with an automatic docker pull first if the image is missing.

The golden rule

A container lives exactly as long as its main process (PID 1). If your command finishes, the container stops. That's why a web server container keeps running, while hello-world prints and exits.

docker stop sends SIGTERM so the app can shut down cleanly, waits 10 seconds, then sends SIGKILL. docker kill sends SIGKILL straight away.

08Level 2 · Hands-on

Your first real container

Run a web server, look at it, go inside it, then clean up. Type these in order.

bash
# 1. Start nginx in the background (-d), name it, and publish port 8080 on your machine to port 80 inside
docker run -d --name web -p 8080:80 nginx:1.27

# 2. Open http://localhost:8080 in a browser, you'll see "Welcome to nginx!"

# 3. See what's running
docker ps

# 4. Read its logs (-f follows live, Ctrl+C to quit)
docker logs -f web

# 5. Open a shell inside the running container
docker exec -it web sh
#    inside: ls /usr/share/nginx/html ; cat /etc/os-release ; exit

# 6. Stop and remove it
docker stop web

09Level 2 · Hands-on

Ports and environment variables

A container has its own private network. Nothing outside can reach it until you publish a port with -p HOST:CONTAINER.

  • -p 127.0.0.1:8080:80 publishes only to your own machine, not to the whole network. Use it for databases on a laptop.
  • -p 80 (one number) picks a random free host port. Find it with docker port web.
  • EXPOSE in a Dockerfile is only documentation. It does not publish anything.

Configuration through environment variables

The same image should run in dev, staging and production. What changes between them (database URLs, API keys, log levels) is passed in at run time as environment variables, never baked into the image.

bash
docker run -d --name db \
  -e POSTGRES_PASSWORD=devpassword \
  -e POSTGRES_DB=shop \
  -p 127.0.0.1:5432:5432 \
  postgres:16
10Level 3 · Your code

How Docker fits into your code

Docker does not change your application code. It wraps around it. You add a few small files to your repository, and from then on the image becomes the thing you test, ship and deploy.

project layout
my-app/
├── app.py              ← your code (unchanged)
├── requirements.txt    ← your dependencies
├── tests/
├── Dockerfile          ← how to build the image
├── .dockerignore       ← what NOT to send to the build
├── compose.yaml        ← how to run app + db + cache locally
├── .env                ← local secrets (git-ignored)
└── .github/workflows/
    └── docker.yml      ← CI builds & pushes the image

What each file does

  • Dockerfile: the build recipe. Lives next to your code and is versioned with it.
  • .dockerignore: keeps .git, node_modules, secrets and junk out of the image.
  • compose.yaml: starts the whole stack with one command for development.
  • CI workflow: builds the image on every push and uploads it to a registry.

The habits Docker pushes you toward

  • Config from the environment. Read DATABASE_URL with os.getenv() or process.env instead of hard-coding it.
  • Log to stdout/stderr. Don't write log files inside the container; Docker collects standard output for docker logs.
  • Listen on 0.0.0.0. A server bound to 127.0.0.1 inside a container can't be reached from outside it.
  • Stateless app containers. Keep data in databases or volumes so any container can be replaced at any time.
  • Handle SIGTERM. Finish in-flight requests and exit cleanly when Docker asks you to stop.

These ideas come from the "Twelve-Factor App" guidelines, and following them makes an app easy to run anywhere, with or without Docker.

11Level 3 · Your code

Walkthrough: Dockerize a Python web app

A small Flask app that counts page visits in Redis. We'll containerize the app here, then add Redis with Compose in section 16.

app.py
import os
from flask import Flask
import redis

app = Flask(__name__)
# Read the Redis host from the environment so the same code works anywhere
cache = redis.Redis(host=os.getenv("REDIS_HOST", "localhost"), port=6379)

@app.route("/")
def hello():
    count = cache.incr("hits")
    return f"Hello from Docker! Seen {count} times.\n"

CMD vs ENTRYPOINT

Dockerfiledocker run imgdocker run img --help
CMD ["python", "app.py"]python app.pytries to run --help as the program
ENTRYPOINT ["python", "app.py"]python app.pypython app.py --help
ENTRYPOINT ["python"] + CMD ["app.py"]python app.pypython --help

Rule of thumb: use CMD for apps; use ENTRYPOINT when the image is a tool (like a CLI) and users pass arguments to it.

Shell form vs exec form

CMD npm start (shell form) runs /bin/sh -c "npm start", so the shell becomes PID 1 and may not pass on stop signals. CMD ["npm", "start"] (exec form) runs the program directly. Prefer exec form.

13Level 3 · Your code

The build cache: order matters

Docker checks each instruction in order. If the instruction and its input files are unchanged, it reuses the cached layer. The first time anything changes, that step and every step after it are rebuilt.

Slow: reinstalls on every code edit

FROM node:22-alpine
WORKDIR /app
COPY . .
RUN npm ci
CMD ["node", "server.js"]

Editing any file invalidates COPY . ., so npm ci runs again (minutes).

Fast: dependencies cached

FROM node:22-alpine
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
CMD ["node", "server.js"]

Code edits only rerun the last COPY (seconds).

  • Put things that change least at the top and things that change most at the bottom.
  • Combine related commands: RUN apt-get update && apt-get install -y pkg && rm -rf /var/lib/apt/lists/*. A separate apt-get update layer can go stale in the cache.
  • Force a clean build with docker build --no-cache .
  • A good .dockerignore prevents junk files (logs, .git) from busting the cache.
14Level 4 · Multi-container

Data: volumes, bind mounts and tmpfs

A container's writable layer is deleted with the container. Anything you want to keep (database files, uploads) must live outside it.

TypeBest forSyntax
Named volumeDatabases and any data that must survive. Portable, backed up with Docker tools.-v pgdata:/var/lib/postgresql/data
Bind mountDevelopment: edit code on your laptop and see it live in the container. Sharing config files.-v "$(pwd)":/app
tmpfsScratch files and secrets that should never touch disk--tmpfs /tmp
bash
docker volume create pgdata
docker run -d --name db -e POSTGRES_PASSWORD=dev -v pgdata:/var/lib/postgresql/data postgres:16
docker rm -f db                     # container gone...
docker run -d --name db -e POSTGRES_PASSWORD=dev -v pgdata:/var/lib/postgresql/data postgres:16
                                    # ...data still there
docker volume ls
docker volume inspect pgdata

# Back up a volume to a tar file in the current folder
docker run --rm -v pgdata:/data -v "$(pwd)":/backup alpine tar czf /backup/pgdata.tgz -C /data .

The longer --mount type=volume,src=pgdata,dst=/var/lib/postgresql/data syntax is more explicit and is recommended in scripts.

15Level 4 · Multi-container

Networking

Docker creates virtual networks so containers can talk to each other. On a user-defined network, Docker runs a small DNS server, so containers find each other by name.

bash
docker network create app-net
docker run -d --name db  --network app-net -e POSTGRES_PASSWORD=dev postgres:16
docker run -d --name web --network app-net -p 8000:5000 -e DATABASE_HOST=db myapp:1.0
docker network inspect app-net   # see who's connected and their IPs
DriverWhat it doesWhen to use
bridgePrivate network on one host (default)Almost always. Create your own so you get name-based DNS.
hostContainer uses the host's network directly, no isolationMaximum network performance on Linux
noneNo networking at allSandboxed batch jobs
overlayOne network spanning many hostsDocker Swarm clusters
macvlan / ipvlanContainer gets its own address on your physical LANLegacy apps that expect to be on the LAN
Gotchas

The default bridge network (used when you don't pass --network) has no name-based DNS. Always create your own network, or use Compose, which does it for you.

Inside a container, localhost means the container itself, not your computer. To reach a service on your computer from a container, use host.docker.internal (built into Docker Desktop; on Linux add --add-host=host.docker.internal:host-gateway).

16Level 4 · Multi-container

Docker Compose: the whole stack in one file

Real apps need several containers: a web app, a database, a cache, maybe a worker. Typing long docker run commands for each gets old fast. Compose describes all of them in one YAML file and starts everything with one command.

compose.yaml
services:
  web:
    build: .                      # build from the Dockerfile in this folder
    ports:
      - "8000:8000"
    environment:
      REDIS_HOST: redis           # the service name doubles as the hostname
    depends_on:
      redis:
        condition: service_healthy
    develop:
      watch:                      # docker compose watch: sync code edits live
        - action: sync+restart
          path: .
          target: /app
        - action: rebuild
          path: requirements.txt

  redis:
    image: redis:7-alpine
    volumes:
      - redis-data:/data
    healthcheck:
      test: ["CMD", "redis-cli", "ping"]
      interval: 5s
      retries: 5

volumes:
  redis-data:
bash
docker compose up -d         # build if needed, create network + volume, start everything
docker compose ps            # status of each service
docker compose logs -f web   # follow logs of one service
docker compose exec web sh   # shell into the running web container
docker compose watch         # live-sync code changes while you develop
docker compose down          # stop and remove containers + network (volumes kept)
docker compose down -v       # ...and delete volumes too (wipes data!)

Open http://localhost:8000 and refresh: the counter goes up. Run docker compose down and up again, and the count survives because it lives in the redis-data volume.

Useful Compose features

  • Profiles: profiles: [debug] marks optional services that only start with --profile debug.
  • Override files: compose.override.yaml is merged automatically; keep dev-only settings there.
  • .env file: variables in a .env next to compose.yaml can be used as ${VAR}.
  • Scaling: docker compose up -d --scale worker=3.
  • Secrets: a top-level secrets: block mounts files at /run/secrets/ instead of using env vars.
Old vs new

docker-compose (with a hyphen) is the retired Python v1. Use docker compose (v2, a Docker CLI plugin). The file is now called compose.yaml, and the top-level version: key is obsolete.

18Level 5 · Advanced

Multi-stage builds

Building software needs compilers, SDKs and dev dependencies. Running it doesn't. A multi-stage Dockerfile builds in one stage and copies only the result into a small final stage. Everything else is thrown away.

Dockerfile (Go)
# syntax=docker/dockerfile:1

# ---------- Stage 1: build ----------
FROM golang:1.23 AS build
WORKDIR /src
COPY go.mod go.sum ./
RUN go mod download
COPY . .
RUN CGO_ENABLED=0 go build -ldflags="-s -w" -o /out/server ./cmd/server

# ---------- Stage 2: run ----------
FROM gcr.io/distroless/static-debian12
COPY --from=build /out/server /server
USER nonroot:nonroot
ENTRYPOINT ["/server"]
Dockerfile (React / Vite front end)
FROM node:22-alpine AS build
WORKDIR /app
COPY package.json package-lock.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM nginx:1.27-alpine
COPY --from=build /app/dist /usr/share/nginx/html
Approach (Go web server)Approximate final sizeContains
Single stage on golang:1.23≈ 850 MBGo toolchain, Debian, source, binary
Multi-stage → alpine≈ 20 MBTiny Linux + shell + binary
Multi-stage → distroless/static≈ 10 MBBinary, CA certs, timezone data; no shell

Smaller images pull faster, start faster and contain fewer packages that could have vulnerabilities. Build just one stage with docker build --target build . (handy for running tests).

19Level 5 · Advanced

BuildKit and buildx

BuildKit is Docker's modern build engine (the default since Docker Engine 23). It runs independent stages in parallel, skips unused stages, and adds powerful RUN --mount options. buildx is the CLI that exposes all of it.

Cache mounts: keep package caches between builds

Dockerfile
RUN --mount=type=cache,target=/root/.cache/pip \
    pip install -r requirements.txt

Secret mounts: use a credential without leaving it in the image

Dockerfile
RUN --mount=type=secret,id=npmrc,target=/root/.npmrc \
    npm ci
bash

Multi-platform images (Intel + ARM)

Apple Silicon Macs, AWS Graviton and Raspberry Pi use ARM CPUs; most servers use x86-64. One command builds both and pushes them under a single tag. Docker picks the right one automatically on pull.

bash
docker buildx create --use --name multi
docker buildx build --platform linux/amd64,linux/arm64 \
  -t yourname/myapp:1.0 --push .

Other BuildKit features

  • Remote cache: --cache-to / --cache-from share layer cache between CI runs (registry, GitHub Actions cache, S3).
  • Bake: docker buildx bake builds many images from one HCL/JSON/Compose definition.
  • Attestations: --sbom=true --provenance=true attach a software bill of materials and build provenance to the image.
  • Heredocs: write multi-line scripts inline in RUN <<EOF … EOF.
  • Build checks: docker build --check . lints your Dockerfile for common mistakes.

--privileged (turns off nearly all isolation), and -v /var/run/docker.sock:/var/run/docker.sock on untrusted containers (gives them full control of the host). Both are occasionally needed for tooling, but understand you are handing over root.

docker ps then shows (healthy) or (unhealthy), and Compose's depends_on: condition: service_healthy waits for it.

Logs

  • The default json-file driver can fill disks. Set rotation in /etc/docker/daemon.json: {"log-driver":"local","log-opts":{"max-size":"10m","max-file":"3"}}
  • Ship logs elsewhere with drivers like fluentd, awslogs, gcplogs, journald, or a collector agent.

PID 1 and signals

The first process in a container is PID 1, which Linux treats specially: it must reap zombie processes and handle signals itself. Run with --init (adds a tiny init called tini) or include tini/dumb-init in the image if your app spawns child processes.

Docker in CI/CD

In a pipeline, the image is the build artifact. Every commit produces an image tagged with its commit SHA, which is tested, scanned and promoted through environments without being rebuilt.

.github/workflows/docker.yml
name: build-and-push
on:
  push:
    branches: [main]

jobs:
  image:
    runs-on: ubuntu-latest
    permissions:
      contents: read
      packages: write
    steps:
      - uses: actions/checkout@v4
      - uses: docker/setup-buildx-action@v3
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: ghcr.io/${{ github.repository }}:${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

GHCR requires lowercase names; if your repository name has capitals, lowercase it in a prior step. GitLab CI, Jenkins, CircleCI and Azure Pipelines follow the same pattern.

Testcontainers

For integration tests, the Testcontainers libraries (Java, Python, Go, Node, .NET and more) start real throwaway databases and brokers in Docker from inside your test code, so tests hit a real Postgres instead of a mock.

Under the hood: how isolation works

A container is not a mini-computer. It is a normal Linux process that the kernel has wrapped in three kinds of fences.

1. Namespaces: what a process can see

NamespaceIsolatesEffect inside the container
pidProcess IDsYour app is PID 1 and can't see host processes
netNetwork stackOwn interfaces, IP, routing table, ports
mntMount pointsOwn root file system built from image layers
utsHostnameOwn hostname (the container ID by default)
ipcShared memory, semaphoresCan't interfere with host IPC
userUser and group IDsRoot inside can map to an unprivileged user outside (rootless, userns-remap)
cgroupcgroup viewSees only its own resource tree

2. cgroups: what a process can use

Control groups cap and account for CPU, memory, disk I/O and process count. --memory 512m becomes a cgroup limit; exceed it and the kernel's OOM killer stops the container (exit code 137).

3. Security layers: what a process can do

  • Capabilities split root's powers into ~40 pieces; Docker grants only a small default set.
  • seccomp blocks dangerous system calls (Docker's default profile blocks around 40+).
  • AppArmor / SELinux add mandatory access control rules on supported distros.

Standards that make it portable

  • OCI Image Spec: an image is a JSON manifest, a config file and a list of tar-archive layers, each addressed by its SHA-256 digest.
  • OCI Runtime Spec: how to run a container from an unpacked file system plus a config.json; implemented by runc, crun, gVisor, Kata Containers and others.
  • OCI Distribution Spec: the HTTP API registries speak.

Because of these standards, an image built by Docker runs on Podman, containerd, CRI-O and every Kubernetes cluster.

bash · see it yourself on Linux
docker run -d --name peek nginx:1.27
docker inspect --format '{{.State.Pid}}' peek     # the container's PID on the HOST
sudo ls -l /proc/$(docker inspect --format '{{.State.Pid}}' peek)/ns   # its namespaces
ps aux | grep nginx                               # it's just a normal host process

When Docker is not the right tool

  • Desktop GUI apps. Possible, but awkward; native installers or Flatpak suit them better.
  • Hard multi-tenant security. Running untrusted customer code needs stronger walls: VMs, gVisor, Kata Containers or Firecracker microVMs.
  • A different kernel. Containers can't run a Windows app on a Linux kernel or need a custom kernel module; use a VM.
  • Very simple scripts. A single static binary or a serverless function may not need a container at all.
  • Stateful databases in production are doable, but many teams prefer a managed database for backups, replication and upgrades.
  • Performance-sensitive I/O on macOS/Windows. Bind mounts cross the VM boundary and can be slow; use volumes or synced files.

Glossary

Build context
The folder (usually .) sent to the builder; COPY can only see files inside it.
Base image
The image named in FROM that yours builds on.
cgroups
Linux feature that limits and measures resource use for groups of processes.
Container
A running or stopped instance of an image: an isolated process with a writable layer.
containerd
The container manager that Docker (and Kubernetes) use to run containers.
Copy-on-write
Files are only copied into the container's layer when first modified.
Daemon
dockerd, the background service that does the work behind the CLI.
Dangling image
An untagged image left behind after a rebuild (<none>).
Digest
A SHA-256 hash that uniquely identifies an image's exact content.
Distroless
Minimal images containing only your app and its runtime dependencies, no shell or package manager.
Entrypoint
The fixed executable a container runs; CMD supplies default arguments.
Layer
One read-only slice of file-system changes in an image.
Manifest list
An index pointing to platform-specific images under one tag (multi-arch).
Namespace
Linux feature that gives a process its own view of a system resource.
OCI
Open Container Initiative: the standards body for image, runtime and distribution formats.
Orchestrator
A system that runs containers across many machines (Kubernetes, Swarm, ECS).
overlay2
The storage driver that merges layers into one view.
Registry
A server that stores and distributes images.
Repository
A named collection of image tags in a registry, e.g. library/nginx.
runc
The reference low-level runtime that actually creates the container process.
Tag
A human-readable, movable label on an image, e.g. 1.27.
Volume
Docker-managed persistent storage that outlives containers.
